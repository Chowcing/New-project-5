# 流水回收站功能设计

## 1. 目标

为个人流水增加回收站，避免用户在流水页或详情页误删记录后无法恢复。

本功能采用三态生命周期：

1. 正常流水：可查询、编辑、统计、导出和推荐。
2. 回收站流水：从正常业务查询中隐藏，但保留完整记录和凭证图片，可由原用户恢复。
3. 软删除流水：在用户从回收站永久删除、清空回收站、到达用户设置的保留期自动清理，或管理员执行删除时产生；不可由普通用户恢复。

回收站支持自动清理。用户可将保留期设置为任意 `1–365` 天，默认 `30` 天；保留期按固定天数计算，并同时作用于回收站已有记录和之后移入的记录。用户仍可随时逐条永久删除或清空回收站。

## 2. 范围

### 2.1 包含

- 用户从流水页或详情页将自己的正常流水移入回收站。
- 用户分页查看自己的回收站。
- 用户逐条恢复回收站流水。
- 用户逐条永久删除回收站流水。
- 用户清空自己的回收站。
- 用户通过快捷选项或自定义天数设置回收站保留期。
- 每日自动软删除已超过当前用户保留期的回收站流水。
- 回收站状态与现有统计、导出、推荐、引用计数、缓存和凭证图片延迟清理规则联动。
- “我的 → 数据管理”增加回收站入口。
- 后端、前端、数据库、接口文档和相关回归测试同步更新。

### 2.2 不包含

- 批量选择部分回收站记录进行恢复或删除。
- 管理员回收站。
- 恢复已经软删除的流水。
- 修改现有凭证图片物理文件延迟清理周期。

## 3. 数据模型

在 `transactions` 表新增：

```sql
trashed_at DATETIME NULL
```

在 `users` 表新增：

```sql
trash_retention_days SMALLINT NOT NULL DEFAULT 30
```

`trash_retention_days` 只接受 `1–365` 的整数。数据库默认值和应用默认值均为 `30`，确保已有用户和新用户在迁移后使用相同默认保留期。

状态定义如下：

| 状态 | `deleted` | `trashed_at` |
| --- | ---: | --- |
| 正常流水 | `0` | `NULL` |
| 回收站流水 | `0` | 非 `NULL` |
| 软删除流水 | `1` | 任意值 |

新增面向回收站查询的组合索引，索引前缀包含 `user_id`、`deleted`、`trashed_at`，支持按当前用户分页查询并按移入时间倒序排列。

同步更新：

- Flyway 增量迁移脚本 `V13__add_transaction_recycle_bin.sql`
- `docker/mysql/init/01_schema.sql`
- `backend/src/test/resources/schema.sql`
- `ExpenseTransaction` 实体的 `trashedAt`
- `ExpenseUser` 实体的 `trashRetentionDays`

现有 `deleted` 继续由 MyBatis-Plus `@TableLogic` 管理，不用回收站状态替代软删除。

## 4. 查询可见性

正常业务中的有效流水统一定义为：

```sql
deleted = 0 AND trashed_at IS NULL
```

以下能力只处理有效流水：

- 流水列表、日期卡片、日期选项和流水详情
- 工作台与统计分析
- CSV 导出
- 智能推荐和快捷推荐
- 重复流水判断
- 分类、支付方式和线上平台的有效引用计数
- 管理后台的普通交易列表、详情和聚合指标

回收站查询只处理：

```sql
user_id = 当前用户
AND deleted = 0
AND trashed_at IS NOT NULL
```

排序固定为：

```sql
trashed_at DESC, id DESC
```

所有查询仍必须显式按 `userId` 隔离。自定义 XML SQL 补充 `trashed_at` 条件；使用 MyBatis-Plus 查询流水时补充 `ExpenseTransaction::getTrashedAt` 条件，避免只依赖 `@TableLogic`。

## 5. 状态流转

### 5.1 移入回收站

用户从流水页或详情页删除时：

1. 校验记录属于当前用户、`deleted=0` 且 `trashed_at IS NULL`。
2. 原子更新 `trashed_at` 为当前服务器时间。
3. 不修改流水的其他业务字段。
4. 不软删凭证图片。
5. 清理与该用户流水相关的统计、推荐和基础数据缓存。
6. 写入 `TRANSACTION_TRASH` 业务审计事件。

重复移入、操作回收站记录或操作不存在的记录时返回明确错误，不静默成功。

### 5.2 恢复

恢复时：

1. 校验记录属于当前用户、`deleted=0` 且 `trashed_at IS NOT NULL`。
2. 校验记录引用的分类、支付方式和非空线上平台仍属于当前用户且有效。
3. 原子更新 `trashed_at` 为 `NULL`。
4. 保留原类型、金额、事项、分类、支付方式、发生时间、场景、备注和凭证图片。
5. 清理相关缓存。
6. 写入 `TRANSACTION_RESTORE` 业务审计事件。

如果必要引用已被删除，则拒绝恢复并给出明确错误，避免把引用无效的流水重新带回正常业务查询。

### 5.3 逐条永久删除

只有当前用户回收站内的记录可以被永久删除：

1. 校验归属和回收站状态。
2. 软删该流水的所有凭证图片记录。
3. 将流水 `deleted` 更新为 `1`。
4. 清理相关缓存。
5. 写入 `TRANSACTION_DELETE` 业务审计事件。

图片物理文件不在请求中立即删除，继续由现有延迟清理任务按保留天数逐个明确路径回收。

### 5.4 清空回收站

清空操作只处理当前用户所有 `deleted=0 AND trashed_at IS NOT NULL` 的流水，并在单个数据库事务中完成：

1. 查询并锁定当前用户待清理的流水 ID。
2. 软删这些流水对应的凭证图片记录。
3. 将这些流水软删除。
4. 为每条永久删除的流水写入 `TRANSACTION_DELETE` 业务审计事件。
5. 事务成功后统一清理相关缓存。

空回收站执行清空时允许成功返回，删除数量为 `0`。任一数据库步骤失败时整体回滚，不保留部分删除结果。

### 5.5 自动清理

自动清理使用用户当前的 `trash_retention_days` 动态判断，不在流水上保存固定的 `expires_at`。因此，用户修改设置后，新保留期同时作用于回收站已有记录和以后移入的记录。

每日 `03:00 Asia/Shanghai` 执行自动清理：

1. 以本次任务开始时间作为统一基准时间。
2. 分批查询 `deleted=0`、`trashed_at IS NOT NULL`，且 `trashed_at` 已早于或等于“基准时间减去所属用户当前保留天数”的流水；每批最多 `200` 条。
3. 每条候选记录在事务中重新校验归属、当前回收站状态、用户当前保留天数和到期条件。
4. 软删记录对应的凭证图片数据库记录。
5. 将流水软删除。
6. 写入 `TRANSACTION_AUTO_DELETE` 业务审计事件，来源为 `SYSTEM`。
7. 按受影响用户统一清理流水相关缓存。
8. 继续处理下一批，直到没有到期记录。

条件更新和受影响行数检查必须保证任务重复触发或多实例同时扫描时不会为同一条流水重复写审计。自动清理日志只记录成功数量和失败数量，不记录用户流水字段、金额、备注、OCR 文本或凭证内容。

自动清理只软删图片数据库记录。现有图片物理文件清理任务仍在每日 `03:30 Asia/Shanghai` 运行，并从图片软删时间开始按现有图片保留期延迟回收物理文件。

### 5.6 管理员删除

管理员从后台删除交易时维持现有语义，不进入用户回收站：

1. 管理员权限和删除原因校验保持不变。
2. 直接软删流水及凭证图片记录。
3. 写入现有管理员审计事件。

管理员普通交易列表不展示用户回收站记录。

## 6. API 设计

所有接口使用 `/api/v1` 基础路径并要求当前用户 JWT 鉴权。

### 6.1 移入回收站

```http
DELETE /transactions/{id}
```

现有路径保留，但语义从“逻辑删除”调整为“移入回收站”。成功返回现有空数据响应。

### 6.2 查询回收站

```http
GET /transactions/trash?page=1&size=20
```

返回 `PageResponse<TrashedTransactionRecord>`。该类型包含回收站列表展示所需的现有流水字段，并额外返回：

```json
{
  "trashedAt": "2026-07-30T14:30:00"
}
```

回收站响应不返回凭证图片元数据或鉴权图片 URL。凭证图片仍保留在服务端，恢复成功后的正常流水响应重新返回图片元数据。

### 6.3 恢复

```http
POST /transactions/{id}/restore
```

成功返回恢复后的 `TransactionRecord`。

### 6.4 永久删除

```http
DELETE /transactions/{id}/permanent
```

仅接受当前用户回收站内的记录。成功返回现有空数据响应。

### 6.5 清空回收站

```http
DELETE /transactions/trash
```

成功返回：

```json
{
  "deletedCount": 3
}
```

接口文档明确永久删除和清空均不可由普通用户恢复。

### 6.6 查询回收站设置

```http
GET /users/me/recycle-bin-settings
```

成功返回：

```json
{
  "retentionDays": 30
}
```

### 6.7 更新回收站设置

```http
PUT /users/me/recycle-bin-settings
Content-Type: application/json

{
  "retentionDays": 15
}
```

`retentionDays` 必须为 `1–365` 的整数。保存成功后立即成为用户当前设置，但不会在当前请求内删除记录；已超过新保留期的记录会在下一次每日自动清理时永久软删除。

## 7. 后端组件职责

### `TransactionMapper`

- 提供正常流水与回收站流水的互斥查询条件。
- 提供带状态前置条件的原子移入、恢复和永久删除更新。
- 提供当前用户回收站 ID 查询和清空所需更新。

### `TransactionService`

- 编排所有状态流转、归属校验、引用有效性校验、图片软删除、缓存失效和业务审计。
- 普通 `delete` 改为移入回收站。
- 管理员调用独立的直接软删除方法，避免复用普通用户删除语义。
- 提供自动清理单条候选记录的事务入口，并在执行删除前重新验证当前保留期和到期状态。

### `TransactionImageService`

- 移入和恢复不调用图片删除能力。
- 图片读取、追加和单图删除只接受正常流水，回收站期间不开放图片操作。
- 永久删除和管理员直接删除继续调用按流水软删图片的能力。
- 清空回收站支持对明确的流水 ID 集合软删图片数据库记录，不执行物理文件批量删除。

### 其他查询组件

`StatisticsMapper`、`AdminMapper` 以及所有直接查询 `ExpenseTransaction` 的服务补充有效流水条件，确保回收站数据不会进入正常业务。

### 回收站设置服务

- 读取当前用户的 `trashRetentionDays`。
- 更新时在服务端校验 `1–365` 的整数范围。
- 设置缩短后不在更新请求内执行清理，由下一次定时任务统一处理。

### 回收站清理任务

- 使用项目统一的 `app.time-zone`，每日 `03:00` 触发。
- 固定每批最多读取 `200` 条到期候选，避免一次加载全部回收站数据。
- 使用统一任务基准时间，并在事务内重新校验每条记录，保证并发安全。

### 8.1 入口与路由

- 在“我的 → 数据管理”中增加“回收站”图标加文字入口。

- 顶部导航使用 `navigationBack.ts` 的安全返回逻辑。

### 8.2 回收站页面

页面包含：

- 标题“回收站”。
- 当前回收站记录数量。
- 当前保留期和“修改保留期”入口。
- 非空时显示“清空回收站”操作。
- 分页记录列表。
- 空状态提示“回收站为空”。

每条记录展示：

- 支出或收入类型
- 金额
- 事项标题，沿用现有标题回退规则
- 分类
- 原发生时间
- 移入回收站时间
- “恢复”按钮
- “永久删除”按钮

回收站页面不提供编辑、复制、创建周期规则、查看或追加凭证等入口。

保留期设置使用 `BottomSheet`，包含：

- `7天`
- `15天`
- `1个月（30天）`
- `3个月（90天）`
- `半年（180天）`
- `1年（365天）`
- 自定义 `1–365` 天整数输入

所有月份和年份文案都对应固定天数，不使用自然月或自然年计算。自定义输入实际字号不低于 `16px`。

### 8.3 交互与反馈

- 流水页和详情页按钮文案改为“移入回收站”。
- 移入确认提示说明“可在回收站恢复”。
- 移入成功提示为“已移入回收站”。
- 恢复成功提示为“已恢复到流水”。
- 永久删除前二次确认并显示“删除后不可恢复”。
- 清空回收站前使用更强的二次确认，明确影响全部回收站记录且不可恢复。
- 缩短保留期时二次确认，明确回收站已有记录也会采用新设置，已超期记录将在下一次自动清理时永久删除。
- 增加保留期或保持相同天数时直接保存，不显示风险确认。
- 操作进行中禁用同一记录的重复操作；清空进行中禁用列表全部状态变更操作。
- 操作成功后刷新当前页和总数；当前分页因删除变为空时回退到有效的上一页。

界面遵循现有明暗主题、移动端优先、图标加文字、可访问名称和最小 16px 聚焦字号规范。

## 9. 错误处理与并发

- 所有状态更新都在 SQL 条件中同时校验 `user_id`、`deleted` 和 `trashed_at`，并检查受影响行数，避免先查后改的竞争窗口。
- 跨用户访问统一表现为“记录不存在”，不泄露记录是否属于其他用户。
- 状态不匹配返回明确业务错误，例如“记录已在回收站”或“记录不在回收站”。
- 恢复前的引用有效性校验失败时，不修改记录状态。
- 清空回收站使用事务，防止图片记录和流水状态不一致。
- 设置接口拒绝小数、非数字、小于 `1` 或大于 `365` 的保留天数。
- 自动清理对每条候选重新读取并校验用户当前设置；设置并发变化时，以事务校验时的设置为准。
- 单条自动清理失败不阻止后续候选处理，任务结束日志汇总成功数和失败数；失败记录保留在回收站并在下次任务中重试。
- 日志和审计不得记录金额、备注、OCR 文本、凭证内容、密码或 token。

## 10. 缓存与审计

以下操作成功后调用现有流水变更缓存失效逻辑：

- 移入回收站
- 恢复
- 永久删除
- 非空回收站的清空
- 自动清理实际删除到期记录
- 管理员直接删除

业务审计动作：

- `TRANSACTION_TRASH`
- `TRANSACTION_RESTORE`
- `TRANSACTION_DELETE`
- `TRANSACTION_AUTO_DELETE`

清空回收站对每条实际永久删除的流水记录 `TRANSACTION_DELETE`，便于按目标流水追踪且不需要在审计日志中记录批量载荷。

自动清理对每条实际永久删除的流水记录 `TRANSACTION_AUTO_DELETE`，审计来源为 `SYSTEM`。未到期、状态已变化或并发处理中未实际删除的记录不写审计。

- 说明用户级保留天数设置接口、固定天数口径、默认值和边界。

同步更新 `docs/production-runbook.md`，说明回收站自动清理在每日 `03:00 Asia/Shanghai` 运行，先软删到期流水和图片记录；现有图片物理文件清理仍在 `03:30` 运行。

本功能不改变生产环境变量、Compose 挂载、Nginx 上传限制或图片物理文件保留天数，因此无需新增环境变量。

## 13. 验收标准

- 用户从流水页或详情页删除后，记录立即从正常流水、统计、导出和推荐中消失，但出现在自己的回收站。
- 用户可恢复记录，恢复后原业务字段和凭证图片保持不变。
- 用户可逐条永久删除或清空回收站；完成后记录进入软删除状态且不能恢复。
- 用户可通过六个快捷选项或自定义整数设置 `1–365` 天保留期，默认值为 `30` 天。
- 每日自动清理会按用户当前设置软删除到期记录；设置变更同时作用于已有和未来回收站记录。
- 缩短保留期不会在保存设置请求内立即删除记录，已超期记录在下一次自动清理时删除。
- 管理员删除仍直接软删除，不进入用户回收站。
- 用户无法查看、恢复或永久删除其他用户的回收站记录。
- 后端完整测试、前端 UI 检查和生产构建全部通过。
